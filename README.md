# techblog-workbooks

Tech blog posts, turned into workbooks. A workbook takes one post, splits what the post builds
into assignments, and gives you tests to write the code against. You rebuild the thing piece by
piece, and by the end you know what the post was teaching because you wrote it.

Two workbooks so far, with more coming. If you've made one from a post, or there's a post you
want to see here, [contributions are welcome](#contributing).

They're generated by [tech-blog-to-workbook](https://github.com/knmn2000/tech-blog-to-workbook),
an Agent Skill that any skills-aware coding agent can run. It reads a post and produces the
assignments, the tests and the problem book.

The collection also has a site, [workbooks.2mbproblems.com](https://workbooks.2mbproblems.com/),
with each workbook's assignments, the project you end up with, setup steps and a read-only copy of
its problem book. The source is in [`site/`](site); it republishes on every push.

## Start a workbook

```bash
git clone https://github.com/knmn2000/techblog-workbooks
cd techblog-workbooks/workbooks/tiny-truetype-renderer   # or workbooks/emudhra-ca-incident
```

With the skill installed, tell your coding agent "set up my workbook". It checks your tools, asks
which language you want, offers to install anything missing, creates your project and opens the
book. Without an agent, double-click `study.cmd` in that folder (or run `.\study`). That opens the
problem book in your browser with Run and Submit working on your code, and offers to create the
project if there isn't one yet.

The book has a problem list with your progress. Each assignment has its statement, a note on what
it adds to your project, hints that open in order, an Editorial with a solution proven to pass, and
an editor holding the assignment's files next to the example test cases. Your code goes in the
project's `solutions/` folder. New files start as the Boilerplate: the input/output code and the
declarations, with TODOs where your work goes. If you'd rather write the includes, the design, the
input reading and the output writing yourself, pick From scratch in the editor, and each file
starts as a comment saying what belongs there. You can also work in your own editor and check from
a terminal with `.\check 01`; the book picks up what you save. The button above the code opens
the current file in VS Code, Cursor, Windsurf, VSCodium, Zed or Sublime Text, or your default app
if none is installed, so your editor's own completion and language server work on it. To use a
different editor, set `WORKBOOK_EDITOR` to its command before starting the book.

Print whatever you like while you test (`cout`, `print`). The checker compares only the output file
your program writes, never what it prints, and the book shows that text under the test result as
"Printed by your program". Use Run on one example to see it.

Each workbook's own README lists what it needs. For TrueType that's g++ with CMake and Ninja, plus
Python 3.11 or newer. The certificate workbook needs Python 3.11 or newer, and only for fresh test
sets also `openssl` on your PATH and the `cryptography` package.

## How checking works

The checker looks at your program's output and nothing else. Each assignment's program runs as
`<program> <input-file> <output-file>`, so the structure and the libraries are your call. Your
agent asks which language you want (C, C++, Go, Rust, Python, JavaScript, TypeScript or Lua) when it
sets a workbook up, and creates that one only.

Expected answers never come from the reference solution. They come from an independent source:
[fontTools](https://github.com/fonttools/fonttools) for most TrueType tests, `openssl` and the
`cryptography` library for most certificate ones. Before an assignment ships, the skill tests its
own tests. The reference solution passes, planted bugs fail (including any bug in the post's own
code), different but correct solutions pass, and a separate solver passes working only from the
problem page.

If a test looks wrong, `.\check 07 -Dispute <test-id> "why"` sets it aside and you carry on.
`.\check 07 -Fresh` hands you a new set of tests you haven't seen.

Your project grows in `solutions/`, in files named for what they do, like `GlyphParser.cpp`, and
later assignments build on earlier ones. Test inputs carry whatever the earlier assignments would
have produced, so a test needs only the earlier files its own assignment uses. When you finish,
the project is a program in its own right, ready to put on GitHub.

## Contributing

To add a workbook, install the [tech-blog-to-workbook](https://github.com/knmn2000/tech-blog-to-workbook)
skill in your coding agent and ask it to turn a post into one. Put the result in
`workbooks/<short-name>/`, add a row to the table above and open a pull request. The site picks the
workbook up on its own; the `site` block of its `workbook.json` says what to install and how to
start it. Before you open the pull request, check that:

- every assignment passes the skill's checks (reference Accepted, planted bugs fail, an
  independent solver passes from the page alone);
- `py -P tools/blank_starters.py` has run, `solutions/` isn't committed (the workbook creates a
  learner's project at setup), and `tools/build_book.py` rebuilds the book with no warnings;
- nothing is copied from the post: problem pages explain in their own words and link to it;
- anything bundled from elsewhere (fonts, libraries, data) has a licence that allows sharing,
  and the licence sits beside it.

To suggest a post, open an issue with the link and what you'd want to learn from it. If
`-Dispute` turned up a test you think is wrong, open an issue with the assignment, the test id and
your reasoning.
